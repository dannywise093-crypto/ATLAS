# LangGraph Checkpoint Migration Design

Status: Implementation contract; D1 schema/index adapter, R2 object API, and a Durable Object coordinator implementation are committed. The LangGraph saver and runtime binding/configuration are not implemented.  
Target dependency lock: `langgraph==1.2.11`, `langgraph-checkpoint==4.1.1`, `langchain-core==1.5.6`  
Target branch: `feat/engineering-design-development`  
Production changes: None

## 1. Verified upstream contract

The MCP lockfile resolves the exact versions above. The upstream `BaseCheckpointSaver` source for LangGraph 1.2.11 confirms these primary operations:

- `get_tuple(config)` and `aget_tuple(config)`
- `list(config, *, filter=None, before=None, limit=None)` and `alist(...)`
- `put(config, checkpoint, metadata, new_versions)` and `aput(...)`
- `put_writes(config, writes, task_id, task_path="")` and `aput_writes(...)`
- `delete_thread(thread_id)` and `adelete_thread(thread_id)`

The base class also exposes delete-for-runs, copy-thread, prune, and delta-channel-history methods. The implementation must explicitly support or safely reject maintenance methods; it must not silently implement unsafe pruning. The default delta-channel-history algorithm walks the parent chain through `get_tuple` / `aget_tuple`, so correct parent configuration and pending writes are mandatory even without a specialized override.

The serializer contract is typed: `dumps_typed(value) -> (type_name, bytes)` and `loads_typed((type_name, bytes)) -> value`. Checkpoint, metadata, and each pending-write value must preserve this type tag and byte payload. Converting these values through ordinary JSON would lose LangGraph/LangChain object fidelity.

## 2. Storage layout decision

Do not put checkpoint payloads in Durable Object JSON records. The current ResearchStorage API caps a DO record at 256 KiB, while checkpoint state and individual channel values can exceed that limit.

Use a split design:

- **R2:** immutable serialized checkpoint and pending-write payload objects. Object keys are generated by the server and include tenant, thread, namespace, checkpoint ID, and payload kind. Never accept a caller-provided raw R2 key.
- **D1:** indexed checkpoint metadata, parent links, ordered checkpoint IDs, pending-write descriptors, and object references. D1 provides queryable history and transactional multi-row updates.
- **Durable Object:** one coordinator per tenant/thread for write serialization, fencing, and a per-thread revision/lease. The DO is the coordination authority, not the bulk checkpoint database.
- **Container:** local cache only. It must be safe to discard at any time.

R2 writes happen before the D1 transaction that publishes their references. A failed metadata transaction can leave an unreferenced immutable R2 object; a bounded garbage collector may remove such objects after a safety grace period. Never publish a D1 reference before the R2 object is fully written and hash-verified.

## 3. Record identity and serialization

Canonical identity is the tuple:

`(tenant_id, thread_id, checkpoint_ns, checkpoint_id)`

The storage layer must keep tenant and thread identifiers separate from user-visible metadata. Every lookup and mutation must be tenant-scoped and must validate the authenticated owner before returning a checkpoint.

Persist at minimum:

- thread ID, checkpoint namespace, checkpoint ID
- parent checkpoint namespace and ID (or null)
- checkpoint serializer type + R2 object key + SHA-256 + byte length
- metadata serializer type + R2 object key + SHA-256 + byte length
- channel versions and any fields needed for index/filter behavior
- creation ordering / timestamp
- pending-write identity: checkpoint ID, task ID, task path, write index, channel, serializer type, R2 key, hash, byte length

Pending writes need stable deterministic identity so retrying the same task write does not duplicate it. Preserve write ordering and LangGraph's special handling of reserved write channels / indexes; verify against the 1.2.11 Postgres and in-memory implementations before coding this behavior.

## 4. Atomic write protocol

### put / aput

1. Validate required configurable fields: `thread_id`, optional `checkpoint_ns`, and parent checkpoint identity from the input config.
2. Serialize checkpoint and metadata using the configured `serde.dumps_typed`.
3. Upload immutable R2 objects and verify returned size and SHA-256.
4. Acquire the thread coordinator lease / fencing token.
5. In a D1 transaction, insert the checkpoint row and update the thread head using compare-and-swap against the expected parent/head revision.
6. Commit and return config with the new checkpoint ID and unchanged thread / namespace identity.
7. Release the lease. A stale writer must not publish after its fencing token expires.

The exact ordering between lease acquisition and immutable R2 upload can be optimized after race tests; the D1 publication must always validate the current fencing token and expected parent.

### put_writes / aput_writes

1. Serialize every write value with the typed serializer.
2. Upload immutable R2 payloads and verify hashes.
3. In one D1 transaction, insert or idempotently upsert the task writes, preserving task path and write index.
4. Reject writes for a missing checkpoint or a checkpoint belonging to another tenant/thread.
5. Duplicate task/write retries must be idempotent.

Checkpoint and pending-write publication must not be represented as one 256 KiB DO JSON value.

## 5. Read protocol

### get_tuple / aget_tuple

- Resolve exact checkpoint when `checkpoint_id` is present; otherwise resolve the latest checkpoint in the requested thread + namespace.
- Load checkpoint and metadata objects from R2.
- Verify object size and SHA-256 before deserialization.
- Load pending writes in deterministic LangGraph order.
- Reconstruct `CheckpointTuple(config, checkpoint, metadata, parent_config, pending_writes)`.
- Missing referenced objects or hash mismatches are hard integrity errors, not empty checkpoints.

### list / alist

- Support optional thread / namespace filtering, metadata filter, before checkpoint config, and limit.
- Return newest-first ordering consistent with the upstream saver contract.
- Do not fetch R2 payloads for rows excluded by metadata filters or pagination.
- Validate tenant ownership before exposing any result.

## 6. Deletion, copy, and pruning safety

- Thread deletion removes D1 rows transactionally and queues referenced R2 objects for delayed garbage collection. The deletion must be tenant-scoped.
- Run deletion requires a verified run-id index and must not delete shared ancestors still needed by live threads.
- Thread copy must copy the complete parent chain and pending writes, not only the head checkpoint.
- `prune(strategy="keep_latest")` is disabled for threads using DeltaChannel until the implementation can retain each channel's nearest `_DeltaSnapshot` ancestor and every intervening write. Silently dropping those rows can corrupt state without raising an error.
- Until copy/prune/run-delete semantics have dedicated tests, fail closed with a clear `NotImplementedError` rather than pretending support.

## 7. Required tests before runtime wiring

1. Typed serializer round-trip for bytes, msgpack objects, metadata, and pending writes.
2. New thread, multiple checkpoints, namespace isolation, exact checkpoint lookup, latest lookup, and parent config.
3. List filtering, before cursor, and limits.
4. Pending writes retain task ID, task path, ordering, and idempotent retry behavior.
5. Concurrent writers with stale parent and stale fencing token: exactly one publication succeeds.
6. R2 upload success followed by D1 failure: no dangling published reference; orphan is collectible.
7. R2 truncation, missing object, and hash mismatch fail closed.
8. Payloads larger than 256 KiB succeed through R2 without increasing DO record size.
9. Restart between checkpoint publication and subsequent invocation: same thread resumes from the durable checkpoint.
10. Tenant A cannot read, overwrite, list, or delete Tenant B's thread.
11. DeltaChannel history reconstructs through parent links and pending writes.
12. Explicit behavior for unsupported delete-for-runs, copy, and prune methods.

## 8. Current implementation status

The initial D1 schema is in `agents/nvidia-deep-researcher/deploy/checkpoint_schema.sql`. It defines tenant/thread/namespace-scoped thread heads, checkpoint descriptors, pending-write descriptors, R2 garbage-collection queue entries, and the supporting history/order indexes. A Python `sqlite3` conformance test exercises schema creation, idempotency, tenant/namespace key isolation, foreign-key relationships, and payload descriptor constraints. These tests validate SQLite-compatible DDL locally; they do not prove that a provisioned Cloudflare D1 database has been migrated or that R2/DO runtime operations work.



The private research Worker also has an initial R2 payload API in `research-worker/checkpoint-objects.js`, routed through `research-worker/index.js`. It generates opaque object IDs server-side, scopes keys by tenant, bounds payload size, stores SHA-256/size metadata, verifies integrity on reads, and prevents cross-tenant reads/deletes. Node tests cover upload, binary round-trip, tamper detection, tenant isolation, deletion, and missing-bucket behavior. The API remains dormant until `RESEARCH_CHECKPOINTS_BUCKET` is provisioned; it is not yet called by a LangGraph saver.

The D1 runtime adapter is in `research-worker/checkpoint-index.js`. It provides scoped checkpoint/thread reads, ordered history, pending-write persistence, delayed-GC queue operations, monotonic thread fencing claims, and a D1 batch publication protocol that compares expected revision, parent head, and fencing token before publishing the checkpoint descriptor. R2 descriptors are validated against the tenant key prefix. Node tests cover atomic publication behavior, stale revision/fence rejection, namespace isolation, and malformed/cross-tenant descriptors.

The coordinator logic is in `research-worker/checkpoint-coordinator-core.js`; it serializes lease operations, issues monotonically increasing fencing tokens, enforces bounded leases, rejects stale holders, and runs checkpoint publication while holding the active lease. The Durable Object wrapper is `research-worker/checkpoint-coordinator.js`, exported from the research Worker entrypoint. It persists its scope, token counter, and active lease in DO SQLite and authenticates its internal requests. Node tests cover competing runners, expiry/takeover, stale publish, scope binding, D1 claim failures, and concurrent acquisition.

These are implementation slices, not a live Cloudflare deployment. The D1 database, R2 bucket, and Durable Object namespace/migration are not provisioned or bound in Wrangler configuration. The DO wrapper is exported from the research Worker, declared in `wrangler.research.jsonc` with a SQLite-backed Durable Object migration, and routed through authenticated `/internal/checkpoint-coordinator/{tenant}/{thread}/{action}` endpoints. The route derives tenant/thread/namespace identity from the DO name and forwards the authenticated request. The required D1 binding is intentionally not declared because no provisioned D1 database ID is available in this repository configuration. An async Python `CloudflareCheckpointSaver` now exists at `src/deep_researcher_agent/common/cloudflare_checkpointer.py`. It uses LangGraph's typed serializer, uploads immutable checkpoint/metadata/write payloads to the authenticated R2 object API, reads D1 descriptors, restores `CheckpointTuple` and parent config, and writes checkpoints/pending writes through the fenced coordinator. `deep_researcher_agent.common.get_checkpointer()` recognizes an explicit `cloudflare://` checkpoint target; PostgreSQL remains the default. The Worker passes the public service URL and tenant to the container only when those bindings are configured. The saver currently fails closed for thread deletion and inherited synchronous methods; deletion, full conformance, runtime restart/resume, and real D1/R2 integration remain incomplete.

## 9. Integration gate

The async saver has focused tests for typed restore, parent config/revision publication, and LangGraph reserved pending-write indices. CI installs the exact locked LangGraph version and runs those tests. Remaining gates: add tenant-scoped thread deletion with delayed R2 garbage collection; run the full LangGraph checkpoint conformance suite; test real D1/R2 operations, payloads above the D1 projection limit, concurrent writers, and process/DO restart; then run the complete NVIDIA workflow through an interruption/restart test and compare state/report behavior against PostgreSQL.

Do not remove `DEEP_RESEARCHER_CHECKPOINT_DB`, change production policy, or enable the Cloudflare checkpoint saver in production until all tests above pass. This document does not authorize production secrets, deployment, or PR merge.
